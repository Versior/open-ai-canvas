# 电商 Agent 与知识库

来源：上游 PR #939（电商 Agent 与后台电商知识库前后端），在本 Fork 中按下文适配。

## 入口

- 用户端：`/ecommerce`，侧栏「电商 Agent」。页面在 `web/src/pages/ecommerce/`。
- 后台：`/admin/ecommerce-knowledge`，菜单「电商知识库」。包括知识来源导入与审核、KB01–KB10 覆盖和阶段模型。
- 旧版电商画布：列表在 `/ecommerce/canvas`，设置在后台「旧版电商画布」（`/admin/settings/ecommerce`），两者只管旧画布，与电商 Agent 互不影响。

## 用户流程

1. 上传商品图和借鉴图，选平台、语言、图片类型、比例和分辨率。
2. 默认先由识图模型看商品图，给出 4 个创意方向。可以直接选、改写名称和描述，或选风格库预设。
3. 策划模型按选定方向写逐张方案：文案、构图、主体和图片提示词；详情页按屏策划。也可以跳过方向直接策划，或用「直出」模式不调用文本模型。
4. 确认后每张图提交一个图片任务（用户自选图片模型，同时最多 3 张），结果进入结果画布，可导出，项目保存在历史里，刷新后恢复。
5. 一套图完成后显示「为你推荐下一组创意方向」。下一组方向是收费的文本任务，只在用户点击后提交。

## 使用前提

- 出图调用工作台图片任务接口 `POST /api/workbench/tasks`，受后台「功能开放 → 图片生成」（`imageWorkbenchEnabled`）控制，该开关默认关闭。关闭时页面在提交前直接提示，不会先发起收费的分析和策划。
- 方向和策划任务以电商项目 ID 作为任务 `projectId`。服务层准入（`ensureTaskProjectActive`）和建单事务（`requireActiveTaskProject`）在画布和业务项目都查不到时，接受当前用户自己的电商项目；建单事务会锁住这条记录，与删除串行。别人的项目或不存在的项目仍然拒绝。
- 电商项目删除后，排队中的方向或策划任务不再发往上游，按失败处理并退回预扣积分。图片任务经工作台接口创建，不带 `projectId`，不受影响。

## 模型与计费

- 识图与策划模型由管理员在「电商知识库 → 阶段模型」统一指定，必须是能看图的文本模型；用户只选图片模型。
- 全部走平台任务，按渠道价格计费；报价拿不到时页面不允许提交。
- 系统渠道模型没有逻辑模型时，页面按渠道 SKU 调 `POST /api/model-catalog/quote` 报价（`modelQuoteRequest` 的 `directChannelQuote` 选项）。其他页面不变：只有视频走渠道报价，图片和文本显示本地价格。
- 后台阶段模型按「渠道 ID + 模型标识」或逻辑模型 ID 匹配用户的可选模型，与服务端校验口径一致。
- 后台没配置时，服务端回退到第一个可用、能看图的逻辑模型；没有逻辑模型时接受页面选中的第一个能看图的文本模型。
- 「视觉质检」角色目前只保存配置，生成流程还没有用到。

## 服务端编排开关 `AI_MODE`

- 本 Fork 未设置时按 `live` 处理：方向与策划任务由服务端改写提示词、注入知识并校验结果。没配 `TEXT_API_KEY` 时，服务端直连调用（如改写风格）也走后台阶段模型的平台渠道。
- 设为 `disabled` 会关闭这层编排：创意方向会拿到未经改写的原始回复，页面无法显示方向，只在排查问题时使用。
- `mock` 只用于自动测试。
- 配了 `TEXT_API_KEY` 时 `TEXT_BASE_URL` 必须是 HTTPS。

## 知识库

- 检索合并三类内容：已审核、来源已启用的数据库条目；还没有初始化过的领域的内置 KB 条目；请求里的方法说明。知识库为空时流程照常可用。
- `POST /api/ecommerce/knowledge/sync` 从固定白名单拉取远程来源，需要外网。
- `backend/cmd/ecommerce-knowledge -bootstrap-builtin -admin <管理员 ID>` 写入内置 KB01–KB10；`-sync` 执行远程同步。
- 方向阶段不注入知识，策划阶段注入。

## 平台规则

- 淘宝/天猫、1688、拼多多、Amazon、Temu、Shopee、TikTok Shop、AliExpress、OZON 有专门的平台规则表（`backend/internal/ecommerceagent/contract.go`）。
- 京东、抖音、小红书、快手等使用平台族设计指导（`design_playbook.go`）和通用规则，不推测没有核实过的平台强制要求。
- 白底、无字主图会清空文案；其余规则写在提示词里，出图后没有像素级检查。

## 数据与迁移

- 八张电商表与知识域索引见 [数据库](/docs/backend/backend-database)。上游 PR 的迁移 78 在本 Fork 中为版本 80，名称 `ecommerce_agent_and_knowledge` 与校验值不变；上游库已有 78 时，启动时随其他上游记录一起顺延两位。
- SQLite 转 PostgreSQL 工具已登记这些表。项目引用的图片受资源删除保护。

## 本 Fork 的适配

- `/ecommerce` 由电商 Agent 接管，旧版电商画布移到 `/ecommerce/canvas`。
- 旧画布的服务端路由与前端协议改名为 `handler/ecommerce_canvas.go`（`RegisterEcommerceCanvasRoutes`）和 `services/api/ecommerce-canvas.ts`，PR 的同名文件保留原路径。
- 任务准入同时保留旧画布的电商能力校验和电商 Agent 的阶段模型校验。
- 图片任务参数只提交工作台白名单内的 `size`、`quality`、`imageResolution`、`count`，不再带 `canvasSize`（后端会整单拒绝未知字段）。
- 图片提交被服务端明确拒绝（4xx，如积分不足、参数无效）时显示「未提交」，处理后可继续生成剩余图片；网络中断、超时和 5xx 仍按「状态未确认」处理，避免重复扣费。
- 没填商品名时，项目名取本轮需求或策划摘要的第一句（最多 24 字），历史里不再全是「未命名商品」。
- PR 引用的「小夜」形象图 `/yoru/yoru-body.png` 不在仓库中，暂用 `/commerce/agent-mark.svg`。

## 已知问题

- 窄屏（390 宽）下全局 Agent 入口的点击区会盖住输入区的发送按钮，属于全局组件，本次未改。
- SQLite 下同时提交多张图片可能出现 `database is locked`，个别计费订单会停在待确认状态；生产应使用 PostgreSQL。
- 京东、抖音、小红书等平台没有核实过的强制规则来源，仍只用平台族指导。淘宝规则里「首图可带促销角标」与旧版电商画布「主图禁促销词」的说法不一致，需要以平台官方规则确认。
