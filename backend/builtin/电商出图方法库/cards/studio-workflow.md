# 在电商生图台里的工作顺序

适用于本轮绑定了生图台商品（工具表里有 `studio_*` 工具）的对话。每一步都以工具返回的真实结果为准。

1. **读状态**：先调 `studio_get_state`，拿到照片（photoId、视角、是否外观依据）、档案、卖点、方案和 `revision`。之后每次写入都传最新 `revision`；收到「商品已在页面上被修改」就重新读取，不要重放旧写入。
2. **看商品**：档案缺失或事实不足、且工具表里有 `studio_inspect_photos` 时，一次传入需要共同观察的照片（外观依据照片 + 吊牌），purpose 写清要核实的问题。只把看得到的写成 visible，吊牌文字逐字照抄。
3. **建档**：用 `studio_update_dossier` 写入事实（每条带 evidence 与 source）、出图时不能改动的外观要点、需要卖家确认的问题。用户在对话里明确说过的事实写 confirmed、source 写「卖家」；推测写 inferred；看不清的写 pending。
4. **问关键缺项**：只有会明显改变结果的缺项（如容量、材质、适用人群、目标平台）才用 `ask_user`，一次合并成一张表单，最多两轮；用户说「按推荐」就用有依据的默认。
5. **写卖点与文案**：同样用 `studio_update_dossier`。卖点用 factIds 指向依据，服务端按依据推导证据；没有可用依据的卖点会保存但不上图，要在回复里请卖家确认。看写入回执里的 warnings，改掉极限词。
6. **排方案**：用 `studio_plan_shots`（action=replace）。主图通常 5 张；详情页按品类排 8–12 屏（见 `cards/category-rules.md`）。图上文案只用已确认的卖点与事实，不写价格。已经出过图的方案只能用 action=update 改镜头。
7. **交给用户出图**：用 `studio_request_generation` 提交要出的 shotIds 和一句说明。它不会提交任务、也不计费；页面显示确认卡，用户选模型并确认后才生成。回复里只能说「已请你在生图台确认」，不要说已经开始生成。
8. **汇报**：先说结果，再列待确认的事实和下一步建议；不堆内部 ID。

权限模式为「需要审批」时，每次档案或方案写入都会先等用户在助手面板批准；只读模式下只能分析，不写入。
